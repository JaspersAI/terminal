# Development

[Contributor guidance](../CLAUDE.md) covers commands and working rules. [How it works](architecture.md) introduces the product architecture. This guide records implementation constraints that matter when changing it.

## Processes and builds

Electron-vite builds main, preload, and renderer, plus the plugin host and store utility-process entries. `src/main/index.ts` wires startup and IPC; `src/main/grid/windows.ts` owns windows. Closing the main window hides the app; quitting stops tasks, hosts, and connections and flushes persistence. Extension windows show the current workspace's grid for their window number.

The plugin view runtime is a separate build, `scripts/build-host-runtime.mjs`, run by `predev` and `prebuild`. Its `out/host-runtime` directory survives electron-vite's builds. It supplies one React instance, ReactDOM, zod, and the SDK per iframe, with import-map shims for their public names. Do not bundle another copy of React into a plugin.

The app bundles the SDK from source using `jaspers-source` in TypeScript, electron-vite, the runtime build, and Node tests. `packages/sdk/scripts/build.mjs` builds the published entries and declarations; the app never consumes that build. Plugins import `@jaspers-ai/sdk`; `/define`, `/skills`, and `/host` are app-facing entries. SDK files import nothing from `src/`.

Assets are never inlined: the renderer's policy is `default-src 'self'; frame-src jaspers-plugin: jaspers-app:`, which refuses data-URI images. Network and filesystem work belong in main behind preload. Main refuses navigation and new windows; allowed https links open in the browser.

## State and persistence

`update` in `src/main/state.ts` applies every state change and notifies subscribers. Preload exposes `window.app`; its exported `AppApi` types the renderer automatically. `actions.ts` validates incoming actions against an exhaustive handler table; tools call the checked mutations directly when they need a result.

The public state replaces provider tokens with `hasToken` and plugin secrets with set/unset indicators. Never put a credential, memory body, or source dataset in that tree. Panel state, output, summary, and published text are part of the tree; preserve their bounds because every push sends the whole tree to every window.

`persist.ts` writes changed branches after a 300 ms debounce, using a temporary file and rename, mode 0600, and flushing on quit:

- `<userData>/state.json`: providers, workspace identities, open windows, sealed credentials, OAuth, the Jaspers sign-in (its registered client, sealed tokens, email, and why a sign-in ended when Account ended it), disabled skills, budgets, and the theme.
- `<userData>/workspaces/<id>/workspace.json`: grids by window number. Version 1 files load into window 1; current files use version 2.
- `<userData>/tasks.json`: tasks and their monotonic id counter.

Registries, connections, plugins, and skills are rebuilt from scans rather than restored from state. Background/login state comes from the OS. A malformed or old persisted value must be checked or migrated before use. Workspace ids must name real workspaces before they can become paths.

The default home is `~/Jaspers`, overridden by `JASPERS_HOME`. It holds plugins, skills, memory, standing instructions, plugin files, and the database. Deleting Electron's `state.json` only restarts onboarding; it does not remove this home.

## Grid and views

The pure grid engine is `src/shared/grid/grid.ts`; integration is `src/main/grid/grid.ts`. How many cells a window's grid has is the workspace's `size` on each of its grids, 16 × 12 by default and 8 × 6 to 100 × 100 by `grid.setSize`, which refuses a size that would leave an element or a written cell outside the grid. No engine function reads the size from a constant: one given a grid reads `grid.size`, and one given bare elements or a rect is given the size too. Element and panel ids are unique across a workspace's windows, never reused, and resolve even in a closed window. A cross-window move updates both grids together.

The cells around the elements are a light spreadsheet: `src/shared/grid/formula.ts` is the rule for what a cell means — a tokenizer, a recursive-descent parser, and an evaluator over about forty-five of Excel's functions, every one of them total and deterministic, answering with a value or with one of `#REF! #DIV/0! #NAME? #VALUE! #NUM! #N/A #CIRC!` rather than throwing. `src/shared/grid/reference.ts` is the rule for pointing at cells while a formula is being typed (where a reference may go, what inserting one leaves, and what a draft reads). The renderer lets the user type in a cell, and `write_cells`, `read_cells`, and `clear_cells` let the assistant do the same. A range selected by hand is the renderer's own state, not the tree's. There are no dates, no wildcards, and no arrays: a range is an argument and never an answer. Tiled elements cannot overlap; floating ones may. Maximizing preserves the original cells. Placement tries the requested cells, nearby cells, then smaller sizes without moving other elements. The assistant must not remove elements merely to make room.

Main checks the whole resulting panel state against the view schema. Views use `usePanelState`, `usePublish`, and `usePublishText`; built-ins and iframe views share the same bridge contract. A panel refresh changes its stamp, which `useData` observes to fetch fresh data. A view with its own live rendering may ignore it.

A panel holds a view and nothing else: no line of text, no stand-in, no message of the app's. What a view's plugin is waiting on the user for is asked in the box of the tile that holds the view (`Need`, from `waitingViews` in `shared/plugins/needs.ts`): the first key the plugin declares and has no value for, then a connection that is `needs-auth`. Until the plugin has it the view is not mounted, and a tile whose views all wait is its box alone. A key goes to main with `plugin.setSecret`, as it does from the field a run asks with; the view mounts once the tree says it is set. Before the assistant runs a plugin's own source, a key the plugin declares and lacks is asked for where the run is, and the run waits for it (`askForUnsetKey`), as a call on a connection does (`askForMissingSecret`); the source is not run without it. The builder's own `run_source` does not ask: a missing key is an answer it reports. The message a missing key fails a call with (`secret-fetch.ts`) is written for the assistant and is not what the user is left reading.

A plugin's `notify` is kept in the inbox and sent to the system's notifications while no window is in front (`fileNotice` in `app/notices.ts`); only a task's notices and the app's own are said in the answer box.

## Requests, tools, and scheduling

`agent.ts` holds the request loop and nothing else; `orchestrator.ts` holds the entry points that start it: the user's request, a task's request or its one call, the welcome's, and what is said unasked into a thread; `loop.ts` holds the requests sent for a tile. `utils/` beside them holds what they compose: cancellation and run events, Eye's record of a run, the limit on background runs, the turns a tile's requests take, streaming, prompt assembly, a round's request and its tool calls, and a chat's thread (where it is kept, what of it a round sends, how it is mended and room made in it). The imports run one way: the loop knows no tool family and no entry point, so the builder can run it and still be one of the orchestrator's tools. `tools.ts` composes tool families under `tools/`: grid, cells, state, conversation, memory, tasks, skills, data, installs, the web, and the builder's entry. Static tool definitions stay with their handlers; skills and source catalogs are rebuilt each round. One tool is the loop's own and in no family: `read_again`, made with each run over that run's own history. `search_web` is in the catalog only while a search provider is set and `fetch_page` always, for the orchestrator and the builder alike, each with its own descriptions, over the search client and the page fetch in `web/`. The builder reads any public https page. The orchestrator reads only an address a search answered or the user typed (`src/shared/agent/web.ts`): it holds the conversation and reads text nobody vouched for, and an address it wrote itself could carry one to whoever wrote the other. Sources are reached through `run_source` and `describe_source`, not one tool definition per source.

A `Request` to the loop carries its prompt (`system()` blocks, static first, and `round()`, what rides on each tool turn) and whether it is quiet. The builder (`build.ts`, its tools and prompt under `build/`) is a quiet run of the loop inside the user's run: its own prompt (the procedure, the rules, and, imported as text through `build/reference.ts`, the templates, the SDK docs, and the SDK's source for `ctx`), its own tools, the parent's run id, so what it is doing shows on the status line as any watched run's does and Stop stops it, and none of its words in the answer box. It is never offered to a task. A build is many short steps: the plugin's shell, the install, then a piece filled in a round with `edit_file` (one passage replaced, `replaceOnce` in `src/shared/agent/build/files.ts`), built by the app and run. So it gets more rounds than a request does (`rounds`). It has a conversation of its own, a thread under `build/<id>` kept as it grows like a chat's. The plugin is installed as a shell, so installed is not finished: a build is over when its plugin is installed and its builder ended the run of its own accord, which the loop tells from running out of rounds (`outOfRounds`). Until then the folder and the conversation stay, however the build ended: a failure, Stop, the app closing, the user's No or a question nobody answered, the builder out of rounds. The next `build_plugin` for that id carries on from both: the builder is told its folder holds what was written, and the failure the caller reads says the build is kept. Once the build is over the conversation is dropped: what was built is in its folder.

The user's requests run side by side. Each starts as it is sent and works on its own copy of its workspace's thread, taken as it starts; what it added joins the thread when it ends, in the order runs end, and the exchange is filed in the chat's log. The store runs ahead of that: as each turn joins a run, its calls before they are run and their results after, the thread is written as it would stand were the run to end there (`standing` in `src/shared/agent/fork.ts`, asked for by the loop's `keep` and done by `keepOpen` in `utils/thread.ts`), so a run that goes no further, or an app that closes under one, leaves the conversation as far as it got. The rules are pure, in `src/shared/agent/fork.ts`: onto a thread nothing else touched the run's turns go back as they are, and onto one that changed meanwhile they go back without their thinking, which a provider ties to what came before it. A run does not join a conversation that is gone, one started over with `/new` since it began or one on a model the app is no longer set to; the chat still shows and keeps what it said. So the thread is only ever changed in one synchronous step and nothing needs a lock. A task's run and the welcome's are held to two at a time (`utils/lanes.ts`). `askUser` queues (`utils/questions.ts`): one question is on screen at a time in each place, the global box or a tile, and in the global box one asked while another of its requests is working carries the request it came from (`askedBy` in `utils/runs.ts`). A place names its workspace with its element, since an element's id is unique in its workspace only. A question's ten minutes start when it is shown: at once in the global box, and in a tile when its box says it has drawn it (`question.seen`), since only a window knows a tile is on the workspace on screen, in an open window, and not under a maximized element. In the renderer a window's requests are a list (`composer/live.ts`), one exchange per request, matched to its run by the name the window gave it, which the run's `start` event says back.

Every element on a grid but the docked chat is a tile of a loop: a piece of work with a record of its own, kept with its workspace (`src/shared/loops/loops.ts`, `src/main/loops/`). It is named by the number in its id and never by what it does: f3 is loop_3 (`loopName`), the name its tile, the tools, and both agents use, which `named` reads however it is written. A loop has one frame, an element on a window's own cells whose panel shows nothing itself (`PanelContent`'s `frame`, which only main makes), and the views it shows are tiles laid out inside the frame: they carry its id as `parent`, and their rects are in the frame's cells, not the window's. Each of the engine's changes takes one layout, the elements laid out together (`layoutOf` and `withLayout` in `src/shared/grid/grid.ts`), and main picks it (`changeGrid` for a window's own, `changeInside` for a frame's, `changeGridOf` for whichever holds an id), so a rect is never weighed against one in other cells; what is inside a frame goes with it, to another window (`moveAcross`) or off the grid. The renderer draws a frame's layout cut to the cells its tiles span (`Board.tsx`, `extent`), so they fill the frame however many cells they took, and a tile in there has no bar, so it is never minimized (`changeMode`) and never moved by hand. It is resized by hand by the edges and corners it turns to the other tiles (`insideEdges` in `grid/edges.ts`): the same drag as a window's elements (`useDrag` in `grid/drag.ts`, given the frame whose layout it resolves against and the cells the board shows, which the pointer is counted in) and the same `element.setRect`. A loop is made with its frame and is closed with it, and both happen in `placeChecked`, `createLoop`, and `removeChecked` and nowhere else: a frame that leaves the grid closes its loop (`closedWithout`), which keeps the record, the frame with every tile and panel inside it, and the conversation in `Loops.closed`, saved in `workspace.json` (version 5; a file written before loops had their name says `flurbs`, `flurbSeq`, `closedFlurbs`, and a tile's tag `flurb`, and reads the same, `retagged`). `reopenLoop` puts them back (`reopened`), keeping the element ids unless one was handed out since, and `deleteLoop` is the only way a record goes for good; `watchLoops` stops a closed loop's run and forgets only a deleted one's thread. Only a deep research loop, one told of the `research` plugin, shows its conversation in its box (`showsChat`); any other shows only its last request, a run's steps and how it ended (`Progress.tsx`), never what was said before, and its agent is told its reply stays folded (`loopRules`). Either box is folded to its line until the label in the frame's bar is pressed (`barLabel` in `box.ts`, over what the box reports of its requests, `boxActivity`, and the loop's status), or a run begins in a frame with no view yet, which opens it until the first view lands (`boxOpens` in `box.ts`, applied in `ElementFrame.tsx`). A saved workspace is made whole as it is read (`adopt`): a file from before loops gets one for every tile, and tiles that lay loose on a window, as a loop's did in 0.3.0 and 0.3.1, go inside a frame where they were. The orchestrator makes a loop with `create_loop` (`src/main/agent/router.ts`, apart from the tool families because it starts a loop's run): `createLoop` makes the record and the frame, half a window unless a size or a spot is given, and the loop's agent starts at once and is not waited for. What that agent places goes inside the frame (`placeChecked`), so the box that is showing the run stays where it is. Its reply is the conversation in the frame's box, and its rules keep its own words there rather than in a note on the grid (`SAID` in `src/shared/agent/prompt.ts`): the note is no agent's to place (`notPlaced` in `src/shared/loops/loops.ts`, which `place_view` holds to), and the views either agent is told of leave it out (`placeable` in `prompt.ts`). The orchestrator routes and holds no tool that drives a view (`orchestratorTools` in `tools.ts` leaves out `ORCHESTRATOR_EXCLUDED_TOOLS`): `create_loop` starts work, `update_loop` hands a request to work that exists, `close_loop` and `reopen_loop` close and reopen one, and `delete_loop` takes one away. The first two are handoffs (`Tool.handoff`): a round whose calls were all handoffs that went through ends the run on what they answered (`handoffReply` in `src/shared/agent/rounds.ts`), the loop's one concession to routing, so a routed request costs one model call before the work starts. What is handed over is the user's request as typed and, under a line that says so, whatever the orchestrator wrote for that work. Everything from the line on counts as nobody's typing (`src/shared/agent/typed.ts`), so a model's words never satisfy what goes by the user's: a key offered to `set_secret`, an address for `fetch_page`, a skill only the user may load. A task's run is the orchestrator's too, and work it starts runs on the task's limits (`Asked.task` in `request.ts`): it is told the task's preface and allowed scripts, and a question it asks starts its wait at once, since nobody may be looking. A task's handoff waits for that work and answers with what it said (`hand` in `router.ts`), so the scheduler's one run of a task at a time and its lanes hold through the work; what it hands on is the task's instructions with whatever the model added (`handedBy`). A request that waited its turn runs in the async context it was sent in (`utils/turns.ts`), so a task's limits never follow the line into the user's own request. A server's own page is shown only when a loop's agent calls its tool; the orchestrator is answered in text. An element has a fourth mode, `minimized`, kept in the engine the way `maximized` is (`restoreRect`, `restoreMode`): it holds the top row of where it stood, a restore resolves like a placement since its cells may have been taken, and one that finds no room throws and leaves it minimized, which a restore by hand turns into a notice. The renderer draws a minimized tile as its bar and keeps what is under it mounted and `inert`, so a view keeps what it holds and its box's question counts as not drawn. The bar's mark is the loop's status as a window knows it: working from the run events every window receives (`working.ts`, a pure reducer, fed by `status.ts`), asking from the questions and key asks the tree places on its tiles. A loop's frame has a cross, which closes the loop (`loop.close`, which is `closeLoop`), and its bar opens the loop's menu (`LoopMenu.tsx`, over `menuOf` in `src/shared/loops/menu.ts` and `endedAs` in `src/shared/agent/transcript.ts`), where its run is stopped and the loop closed or deleted (`loop.delete`, which is `deleteLoop`). View loops (`settings/LoopsDialog.tsx`, over `loopLog`), which Settings opens in its place, lists the workspace's loops, and reopens a closed one (`loop.reopen`). A minimized tile keeps the menu, hung under its bar: with no room to restore it, nothing else by hand could stop or delete what it holds. A minimized element is restored before it is maximized, since its cells were free to others meanwhile. A message typed in the global box that starts with a loop's name, `@loop_3`, is not routed (`addressed` in `src/shared/loops/loops.ts`): it goes to that loop as the user's own words, the address taken off, and the global chat files nothing for it. A thread and its log are filed under a chat's key: a workspace's id for the global conversation, `<workspace>/<loop>` for a loop's. A message typed in a tile's box is `agent:run` naming the tile, and `loop.ts` answers it through the same `userRequest` the global box uses, with what differs handed in: the loop's chat, its whole thread rather than the last three exchanges, a prompt about its own frame and the tiles inside it (`loopPrompt`), tools that change only those (`loopTools`, held to them by `ownTile`), and the frame its questions and key asks show in. A loop's agent is told of its own plugins and the built-ins in full and of the rest by name (`toldOf` in `src/shared/agent/prompt.ts`); `use_plugin` tells it of one of the rest and keeps it on the record, and a plugin it had built is kept the same way. Selection decides what it is told, not what it may call. Either agent reads a loop with `read_loop`: its record, its status, its tiles, and the end of its log with what each run did. A loop's status (working, asking, idle) is read off the runs in flight and what is asked on its tiles, and never stored. A loop runs one run at a time (`utils/turns.ts`). A message for one whose agent is at work waits in its line saying what it is, and the run takes what is waiting after each round of tool calls (`Request.added`, the loop's second change): each joins the thread as a turn of the user's after that round's results, is said as a step of the run's trail (the `steered` event), and answers its sender as one called off does. One that arrives while the reply is being written begins the next run, and so does one sent after `/new` while the old run still works: a run takes nothing once its conversation is no longer its chat's (`stillOn`). Every message added in a round is part of the one exchange, and each is kept whole in the trail, so a key in it is masked when the log is read. Only a user's messages steer a user's run: a task's handoff is never taken, and a run on a task's limits takes nothing. An exchange is still one question and one answer: a user turn straight after a tool turn belongs to the one in progress (`transcript`). One still waiting can be called off by the name its window gave it, which is also how Stop ends one run and no other. A run shows in its loop's frame, and what it asks is asked there. A server's own page opened by a loop's agent is one of that loop's tiles, and only a tile of its own takes the call (`panelTaking`). A loop's agent does not place the docked chat. A loop leaving the open list is what stops its run, and leaving the tree, deleted, is what forgets its thread and its log (`watchLoops`), so every way one goes comes through one rule. In the renderer a frame's box (`grid/LoopBox.tsx` over `box.ts`) follows the runs main says are on its frame, whoever sent them, and draws them with the `Transcript` the global box uses when it shows the conversation, and as `Progress` when it does not. Its command line is always at the top of the box; in a frame with no view in it yet the box open fills the tile under it, and the first view to load folds it.

`llm.ts` selects the request protocol. The `llm/` modules keep each protocol's request builder, response reader, and stream assembly together; `wire.ts` holds shared JSON and streaming helpers. Preserve provider-specific reasoning and tool-call payloads verbatim in assistant turns.

The Jaspers provider is Jaspers' own service, the jaspers-account repo at `https://account.jsprai.com/v1`: OpenRouter's models over Chat Completions and OpenAI's `/audio/transcriptions` for voice, both under one key that Jaspers issues, a JWT naming the user. It is a provider of both kinds, and saving it as the language model sets voice up on it with the same key and base URL unless voice is already on another provider (`voiceWith`, applied in `setProvider`). Onboarding's model step leads with that key and folds the other providers away under it.

A thread is kept whole and sent in part (`src/shared/agent/aside.ts`, applied by `sentOf`, `putAway`, and `shorten` in `utils/thread.ts`). Every round sends the conversation again, so what stays in it is paid for on every round after, and most of a long run is tool answers its model read rounds or requests before. The request at work goes as it is. An earlier request goes as what was said and done: every word, each call by its name and arguments with a long text or list among them cut to its beginning, and a note where an answer longer than 1,500 characters was, which says how long it was, how it began, and the id that brings it back; its turns are rebuilt from their words and calls, without the state they rode with or anything a provider tied to that request (thinking, signatures, reasoning). Inside one request, once its answers come to more than 60,000 characters (`WHOLE_MAX`), every one but the newest round's becomes a note too, and thinking blocks come out with them. Nothing is deleted by any of it: the thread in the store holds every answer and every call as it was, and `read_again`, which the loop offers every run that has tools (`offered` in `utils/thread.ts`), gives a call and what it answered back whole out of that run's own history. A skill's instructions are never set aside: they are how the run is being done, not what it found. Providers cache by prefix, and the newest Claude models tie thinking blocks to the conversation exactly as it stood, so a turn sent one way is sent that way on every round after, in this session and the next. What changes what was sent happens at a boundary, a new request or a request passing its limit, and costs one write of what is by then a short conversation. Never delete an answer from a thread to save tokens, and never rewrite what a turn is sent as from one round to the next. A model can still refuse what it is sent, having a small window or one answer too long to read: the provider refuses the request as too long (`isOverflow` in `src/shared/llm/limits.ts`) or the model's window cuts its reply off (`windowFull` in `src/shared/agent/stop.ts`). Room is made then (`makeRoom`): the request's answers before its newest round are set aside whatever they come to; then the answers of the round just run are withheld, largest first and no more than bring what is sent to two thirds of what it was, each leaving a note that it was never shown and that a source's rows are in the store; and only when no answer is left does the thread keep just its end. Turns are replaced in the run's copy, never rewritten, and when the run ends they go back to the thread with what it added (`putBack` in `src/shared/agent/fork.ts`) unless another run changed the thread meanwhile. The one cut by count is the global conversation's, between requests: it goes on with its last three exchanges (`recent` in `src/shared/agent/history.ts`), where a loop's goes on whole. The system prompt holds only what is the same every round. What is true this round (grid, focused element, clock, tasks, filed sources) rides on the turn being sent as its `context`, and each protocol says it its own way: Anthropic as a turn-scoped system message, or a kept text block where that is refused; the OpenAI shapes as the newest state at the very end of the request. Keep volatile text out of the system prompt and out of tool descriptions, which render in front of everything. After changing prompt assembly, check the `cached` figure on the `[agent]` log line: a second round that reads nothing from cache means something in the prefix moved. Through OpenRouter, which the Jaspers provider is behind its key, Anthropic's models cache only where the request asks: a tool loop asks for automatic caching and marks the system prompt, and the `[agent]` log line's `cached` and `wrote` counts show what the provider served and took.

The Anthropic adapter's extras (adaptive thinking, effort, turn-scoped state, fallbacks, a call's input sent as it is written) are found out rather than declared: one a model or proxy refuses with a 400 is left off for it for the session. The last is `eager_input_streaming` on each tool of a streamed request: without it the provider holds each value of a call's input back until it is whole, and a long call is minutes of a stream with not one byte in it, which the limit on silence would cut off. Requests stream whether or not anyone reads the pieces, and a stream is held to its silences, not its whole length. A run someone watches, the user's own and any loop a tool runs under it, says what its model is doing while the reply arrives (`saidOf` in `src/shared/agent/rounds.ts`): its thinking, and a tool call still being written after five seconds, by its tool and how long so far, in one line that is said again as it goes on. Thinking is how a run stands and no step (`thought` in `src/shared/agent/agent.ts`): every round says the model is asked, each thought takes that line's place as it comes (the `thinking` event), and the line goes when the model says or does anything, so a trail holds what was said and done however long the model thought, and a run's filed steps hold no thinking. The Anthropic adapter asks for summarized thinking; the Chat Completions adapter reads what OpenRouter sends unasked (`reasoning_details`, or the `reasoning` string), which is how a model on the Jaspers sign-in says its thoughts. Each call is a step of the trail as it is made, however often its tool is called, and a source by the plugin doing the work (`callLine`). What the model said before a round's calls is told whole once that reply is (the `said` event): a box that drew the words as they arrived keeps them in the trail, ahead of those calls, for as long as the run works. The thread keeps them, and a run's filed steps leave them out, since a loop's log is read again by models (`read_loop`). What happens to a run that is no step of its own (a provider's failure waited out, a reply cut off, a conversation made shorter, a package fetched for a build, the wait for the app to build a plugin) is said in the same words in the log and on the status line (`telling` in `src/main/agent/utils/runs.ts`). Each stream reader reports only a call's start (`onCall`): how much of an input has arrived is no measure, since a provider may hold it back until it is whole, and a call's input is never put on a status line. The loop retries rate limits, overload, server errors, and dropped connections with backoff; never runs the tools of a reply cut off at its output limit; and mends a thread when the refusal is about the thread: stale thinking is dropped, and a conversation too long for the model has room made in it, a few times a run at most.

Threads are scoped to workspace and provider/model identity. `thread-file.ts` restores each workspace's thread from the store at startup and saves it whole as each turn joins a run and again as the run ends, without turn state or thinking blocks: a restart comes back to the conversation the next request would have read had the app stayed open, however old it is. A run that ended early keeps what it got done, closed off with why (`closeOff` in `src/shared/agent/history.ts`): the user stopped it, it failed, or the app closed under it. Calls nothing answered are answered that they did not finish and the thread ends on the assistant's turn, which is the shape every provider takes back. Never drop a run from its thread: a conversation a provider refuses outright is started over with `/new`. `/new` starts a thread over. Tools marked `readsOnly` run side by side within a round; the rest run alone, in call order. Every tool gets the run's abort signal. A source's answer, a query's, and what `read_again` brings back go to the model whole, however long (`whole` on the tool): rows are never cut. Any other tool's answer over the cap is cut with a note. Transcript display masks secrets, strips tool rounds, and retains the original `/name` input rather than expanded skill text.

The chat is not the thread. A thread is what the model works from; the chat is what the user saw, and every exchange of it is filed in the store's `exchanges` table as it was shown (`file` in `utils/thread.ts`): when a run ends or is stopped, when a task or the welcome speaks, and for `/new`, which reads in the chat as the line where the assistant's memory begins. Keys are masked when an exchange is filed and again when it is read. Nothing a thread goes through (the cut to three exchanges, room made in it, another model, `/new`) touches the log. The user can read back further than the model is sent, so the prompt's rules say how many exchanges that is, by the same count the thread is cut to, and to ask rather than guess about anything before them. `agent:history` reads it a page at a time, the newest or the one ahead of an exchange by its id, and answers from the thread's last few when the store is down. `Transcript.tsx` asks for the page ahead as the reader nears the top (`useEarlier`) and holds what is being read in place when it joins; a reply landing at the end goes under the pages already read (`rejoin`).

Citations are read off every source run in `sources.ts`, whoever asked for it, since a view may publish `[^id]` beside a quote for the model to cite. Main keeps them by workspace beside the datasets, bounded, and never in the state tree. The reply that ends a run keeps the ones its markers name on its assistant turn, which no provider is sent and a kept thread retains; the answer in flight hears them as a `citations` event once it is whole, and history carries them on each exchange, masked like the reply. A marker whose id no run gave shows as nothing, so the model can point at a source but cannot make one up.

Tasks use one timer and skip interval slots missed during a long run. They may use a fixed interval or a weekday/local-time rule with an IANA time zone; the latter keeps its hour across daylight saving changes. `parseClockRule` validates rules at IPC and model boundaries. The tool adapter alone handles JSON strings and the model-facing `market` alias. Unknown weekdays are errors, never silently omitted.

Tasks run on their own workspace, with fresh conversations and no interactive secret prompts. A command the user has not allowed a task asks at its run, and `askUser` shows one question at a time: one asked while another is up waits behind it, and its ten minutes start when it is shown. Watch tasks compare stored observations before waking a model. Daily token budgets apply to background model rounds, not user requests. Quiet successful calls stay quiet, and so does a run with no outcome: a task's model answers only when the user needs to hear something (what the instructions ask to be told, a finding, a problem to act on), and an empty answer says nothing. Nobody needs to hear that a job ran. A reply joins its workspace's thread as a note naming the task and the assistant's own turn, never a user turn, so the chat shows it and a follow-up can refer to it; it lands in one step, since no run writes the thread while it works. Failures stay notices. Either way a notice is filed in the inbox, and one standing for the chat on screen shows the chat instead of its line.

The Composer keeps controls and animation in `Composer.tsx`. `request.ts` owns recording, transcription, requests, streaming, and stopping; `conversation.ts` owns history visibility, reading the chat a page at a time, and answer/notice timers. `reveal.ts` owns whether the composer is up. A run on screen holds it up; one whose box was dismissed works on out of sight (`hidden` in `live.ts`), lets the composer go, and is in the conversation whenever the composer brings that up, until its reply or a request sent beside it puts it back in the box. Preserve Escape ownership, settings modality, microphone release during permission prompts, and timer cleanup when changing these hooks.

## Plugins, connections, and trust

Plugins are folders under `<JASPERS_HOME>/plugins/<id>`, with `plugin.tsx` and a matching definition id. Official plugins live in separate repositories. Saving a plugin rebuilds it; a failed build retains the last good registration. Builds are serialized per plugin. Skill-only edits rescan skills without rebuilding code.

The loader makes a browser bundle and a definitions bundle. The definitions build is neutral with browser main fields, evaluated with a timeout and a small `require` allowlist. Main reads schemas; a utility process runs function sources, `start`, and jobs. A VM and utility process contain faults, not malicious code.

- Capabilities are checked on both sides of RPC. Keep credentials in main; plugins receive configured model/tool calls instead of keys.
- `ctx.workspace` follows the source call and its jobs. At startup, without a caller, it is null.
- File capabilities confine paths after resolving symlinks. Writes never traverse a link, removals unlink links themselves, and openable file types are allowlisted.
- Plugin fetches are limited to declared hosts, including redirects.
- Host shutdown aborts jobs and waits briefly for them to save before killing the process. Rebuilds wait for the old host to stop before replacing it.
- A host starts with its build only when the plugin defines `start`, and only that host comes back on its own after a crash. Any other starts on the first source run and stops after five minutes with no run, job, file watch, or live value.
- Live values use their own subscription channel, not the persisted state tree.

A plugin the assistant built carries `.jaspers-build.json`: the purpose, the request, and the approved envelope (hosts, capabilities, secrets, connections, packages, frames). The builder writes into `<JASPERS_HOME>/.build/<id>` until the user approves, outside the watched roots, so nothing of it is evaluated, and the folder stays there until the plugin lands; a yes writes the record, installs the packages, and moves the folder under `plugins/`. The question shows the envelope and the files as they stand, which for a plugin installed as a shell is its outline, and says the builder goes on writing: what a yes covers is the envelope. Every build of a folder with a record compares what the definition and package.json declare (`envelopeOf`) with what was approved (`widened`) and fails naming anything wider; a widening is approved through the same question, showing only what is new. Packages come from the npm registry through `packages.ts`: abbreviated listings, the highest matching version, dependencies followed and optional ones skipped, tarballs checked against their integrity and unpacked with the archive checks, npm's layout, no lifecycle scripts. A function source's `ctx.fetch` fills `${secret:KEY}` from the plugin's declared secrets, which main sends the host with each run; the value reaches only a declared host, as a connection's headers do.

Connections are declared by plugins; a connection added in Settings is written as a plugin folder with an ownership record. Main keeps one MCP client per connection. Unchanged specs retain the client; changed ones reconnect. Missing secrets use the same secure prompt regardless of who called. Scheduled tasks fail instead of opening it. OAuth starts only through explicit authorization. An `oauth` connection whose server's protected resource metadata (RFC 9728) names Jaspers' Account among its authorization servers takes the app's own sign-in with Jaspers as its bearer: it runs no flow of its own, reads `needs-sign-in` while the app is signed out (Sign in with Jaspers is its action), and follows the sign-in as it begins and ends. Its 401 renews the sign-in once and sends again; a 403 is shown in the server's words and not retried. Every other `oauth` server signs the user in through the connection's own flow, as before.

## Signing in with Jaspers

Account (`https://account.jsprai.com`) is the OAuth 2.1 authorization server every Jaspers service trusts, and the terminal is one of its public clients. `src/main/jaspers/session.ts` runs the flow with the MCP SDK's client auth helpers: the system browser, a loopback on a port of its own (`src/main/app/loopback.ts`, which the connections' OAuth uses too), PKCE, a registration with Account each time, and `resource` set to the issuer itself, the platform, so one token serves the gateway, the screener, and Hub. `jaspers.ts` gives it the tree for its store, `safeStorage` for its seal, and the browser; the renderer sees only `jaspers: { signedIn, email, reason }`. Settings' Account row, shown while signed in, is a link to the account's page (`accountPage`) and no pane, and it names no address either: the renderer asks over `shell:open-account`, and main, which knows where Account is, opens it. The rules are pure in `src/shared/app/jaspers.ts`.

Account rotates refresh tokens and reads a spent one presented again as theft, ending the grant, so the session renews once however many requests ask at the same moment, before a token runs out or after a 401, and never presents a refresh token twice. A refresh Account refuses (`invalid_grant` and its kin) signs the user out with the reason, which Settings > LLM shows on the Jaspers provider's Account row; a passing failure keeps the tokens for the next try. Signing out (`jaspers.signOut`; no screen offers it, and the account's page disconnects the app instead, which the next refresh finds) revokes the refresh token at Account, best effort, and forgets the sign-in; the providers set to Jaspers stay and wait for the next one.

The Jaspers provider has no key: `getProviderConfig` gives it the account's fetch, which adds the bearer, renews once on a 401 and sends again, and throws a 402, a 403, or a 401 on the token just issued in the service's words, never retried and never a sign-out: the service refused, and the sign-in stays good at every other. The wire (`post`, `sse`) sends every provider's request through its config's fetch. Choosing Jaspers as a provider needs the sign-in, and signing in sets Jaspers up only where the user has no provider.

To develop against a local run of jaspers-account, set `JASPERS_ACCOUNT_URL` (for example `JASPERS_ACCOUNT_URL=http://localhost:3350 npm run dev`): the sign-in, the gateway (`${account}/v1`), and the test of which servers sign in through Jaspers all follow it, and the Jaspers provider's base URL is derived from it rather than read from Settings. A value that is not an http(s) URL stops main as it loads.

Jaspers Hub (`https://hub-api.jsprai.com/v1`, the jaspers-hub repo's API) is read by `src/main/hub/hub.ts`: its listings and items plainly, and what it holds of the user, a handle claimed, and a version published through the account's fetch, every request with a time limit. Its answers are read through `src/shared/hub/hub.ts`, and the renderer asks for them over IPC (`hub-ipc.ts`). To develop against a local run, set `JASPERS_HUB_URL` (for example `http://localhost:3360/v1`); a value that is not an http(s) URL stops main as it loads, and only Hub's own address may be plain http. Publishing (`publish.ts`) takes only a plugin whose origin is `local` or `built`, or a skill whose origin is `local`, and packs its folder without `node_modules` and without any name that starts with a dot, refusing one that holds a link.

Credentials are sealed with Electron `safeStorage`; systems without encryption use the documented plaintext fallback with a warning. Never quote secrets in errors or logs. A key offered by the model is accepted only if the user supplied that exact text; otherwise ask through the secure field.

Stdio `node` commands run Electron's Node. Startup merges the login shell's PATH so Finder launches can find tools such as `uvx` and `npx`. Shutdown closes clients and their children.

## Plugin view isolation

`jaspers-plugin://<id>/` serves each plugin's page and bundle; `jaspers-host://runtime/` serves the runtime. Only allowed paths are served, with confinement checks. The iframe bridge checks `event.source` on both sides and uses the frame's workspace, not a workspace claimed in a message. A framed third-party page must not gain access to the parent bridge.

The page links the theme, `src/host-runtime/theme.css`, which the runtime build copies beside the runtime and the renderer's stylesheet imports; it is the one place the colors are written. Main sets `nativeTheme.themeSource` from the Appearance setting, and that decides `prefers-color-scheme` in the renderer and every frame at once.

The page denies network and workers. A nonce permits its inline import map. Declared frame origins must be exact https origins. Plugins that frame other sites use `allow-scripts allow-same-origin`, giving their own plugin origin; other plugin frames use `allow-scripts` alone. Neither gets forms, popups, or app navigation. Keep `worker-src 'none'`: workers otherwise introduce their own network context.

Opaque frames post to `'*'`, so source checks are essential. Subscription replies must name the subscription before its first change arrives. A rebuild remounts frames by build version while retaining panel state.

## A server's own pages

A connection's server may ship a page for a tool: the MCP Apps extension, `io.modelcontextprotocol/ui`. Every client declares it. `readTools` splits what a server lists: the tree carries the tools the model may call, each with its page, and a tool for a page alone stays out of the tree and in `Live.tools` beside the client. `call` takes who is asking and refuses a caller the tool does not name, so every caller has to keep coming through it. The rules are pure, in `src/shared/plugins/apps.ts`.

`jaspers-app://<name>.<plugin>/<encoded ui:// address>?k=<key>` serves a page: one origin per connection, the page as its server wrote it, with the policy it declared as a response header. `appPolicy` builds that header and leaves out a declared domain that is not an origin; never put a server's string into it unchecked. Only a page a panel opened is served, and only at the address that panel was given. The key is made for each open (`app-pages.ts`): a frame can send itself anywhere on the scheme, and the rest of an address is the connection's id and the page's name, which another server's page can work out. The frame is `allow-scripts allow-same-origin allow-forms`, so its origin is its connection's and never the app's; forms are allowed so a page's script can take a submit, and `form-action 'none'` keeps a form from going anywhere. It is one frame, not the extension's sandbox proxy: the scheme, the header, and the key give what the proxy is for.

`core/app` hosts the page with `AppBridge` from `@modelcontextprotocol/ext-apps`, pinned at 1.7.5 since 2.x needs MCP SDK v2. The bridge is connected before the frame is given its address, and nothing is sent to a page before it says it is initialized. A page may say so more than once, when it mounts twice or loads itself again; each time it is told the same result, and the panel's call is made once for the frame (`app-tell.ts`). A page that is going is told (`ui/resource-teardown`) and given half a second: React removes an element the moment it stops drawing it, and a page whose frame has left the document hears nothing, so the view makes and removes its frame itself and moves one that is leaving out of sight until its page has answered. From then on what that page asks is refused. Everything a page asks crosses IPC named by its panel (`app:open`, `app:run`, `app:call`) and is checked in main against that panel: the connection it shows, the user's yes for that connection (`allowedApps`, main only, recorded against where the connection points), the panel's own tool (one the model may call, that has a page), and for a page's own call a tool its server offers to a page, asked from the address of the panel's latest open, so a frame that has been replaced, or whose panel was given another connection, reaches nothing. What a page may ask at all is the capability list in `App.tsx`; adding to it decides what a server's code may do.

A panel keeps the one call it shows beside its workspace, `workspaces/<id>/apps/<panel>.json`, so a restart does not call the tool again. The kept call answers while the panel's arguments are its own and its refresh stamp is not newer. The assistant's `run_source` on `core/mcp` places the view with the call it just made, and only in a run the user started; a call that found the grid full is held for a view placed soon after.

## Store, skills, and installs

The SQLite store runs in a utility process because its calls are synchronous. Source results are recorded best-effort without blocking callers. Queries use a read-only connection, one SELECT/WITH statement; a timed-out query kills the process, which restarts on demand. Notifications, usage, watch observations, each chat, and the end of each thread also live there, a chat being a workspace's own or one of its loops'. An exchange is filed with the steps its run took, and a run that failed is filed with why; the thread drops a failed run, the log does not. The file is at version 8, which named the column those two are filed under `chat` and added the steps and the error; a file from before is carried over on its first open, and a build from before refuses it. User data has no automatic expiry except explicitly bounded histories; the chat is not one of those, and is kept whole.

Skills follow Agent Skills frontmatter and are loaded in tiers: catalog, instructions, then files. `skillUsable` is the shared access rule. A user-only skill is readable by the model only while a `/name` for it is in the thread, which holds the last three exchanges. Skill scripts are never executed. File reads are confined and bounded; editor writes require the previously read hash and refuse installed/plugin skills. The assistant writes a skill only through `write_skill` (`skill-write.ts`, its rules in `src/shared/skills/skill-draft.ts`): the user is shown the whole `SKILL.md` and it is written on their yes, as a new skill of their own, never over one that exists, and a task's run is not offered the tool. Preserve whole skill-content turns if changing conversation trimming.

Plugin and skill installers share download, hash, staging, and locking in `archive-fetch.ts`. Archives are checked entry by entry with path and size limits and no links. Nothing is evaluated before confirmation. A plugin's install is staged and committed in `install-stage.ts`, which runs without Electron: `install.ts` holds a stage under a token while the prompt asks, and what a Jaspers sign-up comes with (`default-install.ts`) is committed without a prompt, the sign-in's consent standing for it: only `jaspers/screener-mcp` and `jaspers/research`, one after the other, only while setup is open, each only when Hub says it is Jaspers' own and the version reviewed, and only where no plugin of its id exists. One that fails is a notice and does not stop the other. An archive from Hub is refused before it is unpacked unless its SHA-256 equals the `X-Hub-Sha256` it came with. The assistant's `install_plugin`, `install_skill`, and `add_connection` (`src/main/agent/tools/installs.ts`) stage through the same `prepareInstall`, `prepareSkills`, and `addConnection` the panes use, and confirm only on the exact Install (or Add connection) answer to an `askUser` question showing what was staged; anything else cancels, and a task's run refuses them. A folder without an install record belongs to the user and cannot be replaced by an update. Updates move the old folder aside and restore it if replacement fails. Removal uses the trash and respects ownership records.

## Eye

Eye is `src/main/eye/eye.ts` (the timer, the frames, the run records, the telemetry file), `events.ts` (the telemetry file's line, appended on the turn it is recorded), and `upload.ts` (the queue on disk, sent oldest first), over the rules in `src/shared/app/eye.ts`: what a frame is, what blocks one, what a run's record holds and how it is masked and capped, what a telemetry line may hold, what the queue may keep, and how a server's answer is read. On or off is the only setting a window may change, through `eye.set`. Consent is to a wording, by number: `EYE_CONSENT` changes whenever what Eye records changes, a stored yes to an older number reads as not asked, and recording stays off until the new wording is answered. Where a batch goes and the token it carries are constants there, `EYE_ENDPOINT` and `EYE_TOKEN`, not settings: the token ships in the app, so it is a filter against strays and not a secret. An install is told apart by `eye.install`, a UUID `persist.ts` makes once and keeps, which main alone can set; it goes with every batch and is what the server files a session under. No tool reaches any of it. `record` writes its line synchronously, as `persist.ts` writes the tree on quit: `endSession` records the session's closing line from `before-quit` and the app goes on that turn, so a line handed to a promise there would never reach the disk and every clean quit would read as a crash.

A run's record is assembled in `src/main/agent/utils/record.ts` from what passes through `emit` in `runs.ts` and what `calls.ts` notes of each tool call, and written by `recordRun` the moment the run ends: the request, the reply or the error, the outcome, and every tool call with its arguments and result, every secret the app holds masked out first (`knownSecrets` in `settings.ts`, the same list the transcript is masked with). A batch is one session's folder as `multipart/form-data`: `session` (the folder's stamp), `install`, `app`, `platform`, `closed`, up to 40 `frames`, up to 50 `runs`, and the `events` file once the session is closed. The recorder's counters on the tree wake the uploader, so a frame or a run goes within seconds of being written; a pass every five minutes is the safety net. `batchAccepted` reads the answer the way the server means it: 2xx and 4xx are final and the batch is deleted here, 408, 429, and 5xx mean later. So a wrong token is not retried, and a change of token has to reach the app in a release before the server stops accepting the old one.

The server is [JaspersAI/jaspers-eye](https://github.com/JaspersAI/jaspers-eye): a small Node service at `https://eye.jsprai.com` on the app EC2, filing frames and telemetry lines into a database of its own on the cluster. Its README holds the contract from the other side and the queries.

## Packaging and publishing

`electron-builder.yml` packages `out/` and dependencies for the platform `npm run dist` runs on: a macOS arm64 app with `build/icon.png`, the logo on macOS's icon grid, as a DMG and the zip installed Macs update from; or a Windows x64 NSIS installer, one-click and per-user, with `build/icon-win.png`, the logo's square tile. The Mac app is signed with the Developer ID when the keychain has it (see [Releasing and updates](#releasing-and-updates)), under the hardened runtime, which allows it only what `build/entitlements.mac.plist` names: V8's JIT and the microphone. Its Info.plist carries the Desktop and Downloads usage strings macOS shows when a Pro mode command first reads them (`extendInfo`). Plugins are not bundled. Esbuild's native binary is unpacked beside the asar; set its packaged path before loading esbuild, which is imported lazily to avoid hoisted requires.

To publish the SDK, bump `packages/sdk/package.json`, build and check it, then publish from `packages/sdk` with `npm publish --access public`. Its `prepublishOnly` rebuilds the package. Publishing is a separate explicit action; a local SDK build does not publish anything.

CI (`.github/workflows/ci.yml`) runs the format check, typecheck, and tests on every push to main and every pull request, on Linux without Electron's binary; nothing it runs may start Electron.

`preview.yml` builds the DMG on a macOS runner for a pull request from a `ship/` branch, uploads it to a public Vercel Blob store with the `BLOB_READ_WRITE_TOKEN` secret, and links it in a comment on the pull request. It is the real app, ad-hoc signed, since the Developer ID certificate never meets a pull request's code: the first open needs Open Anyway in System Settings, it shares the installed app's data, and it refuses every update it downloads. Only Ship's branches build because a macOS minute counts as ten while the repo is private.

## Releasing and updates

`release.yml` runs when a `v*` tag is pushed, one job per platform, side by side. On a Windows runner it builds the installer, signs it with Azure Artifact Signing, and uploads it with its blockmap and `latest.yml` under `win/`. On a macOS runner it builds the app, signs it with Jaspers Inc.'s Developer ID Application certificate, has Apple notarize it, and uploads the DMG and the zip with their blockmaps and `latest-mac.yml` under `mac/`. Both go to the public `terminal-releases` Blob store, into the folder `publish.url` in `electron-builder.yml` names with `${os}`; `scripts/upload-release.mjs` does the uploading for both. Once a platform's feed is up, the job copies its installer to a name without the version, `win/Jaspers-Terminal-Setup.exe` and `mac/Jaspers-Terminal-arm64.dmg`, rewritten each release and cached for a minute like the feed. The website's download buttons link to `https://account.jsprai.com/download/mac` and `/download/windows` (`jaspers-account`), which redirect there, so they always get the version installed apps are offered and the page never names the store. The tag must match `version` in package.json. The run's summary links the installer, the DMG, and those two download links. The Windows job's secrets are `AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, and `AZURE_CLIENT_SECRET`, a service principal (`jaspers-terminal-release`) allowed to sign with the `jaspers-terminal` certificate profile on the `signing-jaspers` account; the Mac job's are `CSC_LINK` and `CSC_KEY_PASSWORD`, the certificate, and `APPLE_API_KEY`, `APPLE_API_KEY_ID`, and `APPLE_API_ISSUER`, the App Store Connect key it notarizes with. Both upload with `RELEASES_BLOB_TOKEN`, the store's read-write token. Whoever holds that token decides what every install updates to, so the store is its own, apart from the previews'.

To release, in this order:

1. Bump `version` in package.json and commit. The workflow refuses a tag that does not equal `v` + that version.
2. `git tag v<version>` on that commit, then `git push origin main v<version>`. The tag push is what triggers `release.yml`; a push of main alone releases nothing.
3. Follow the run under Actions > Release. Windows takes about five minutes: Electron and NSIS downloads, the signing module install, four signatures, the upload. The Mac takes as long plus notarization, a few minutes as a rule and at times much longer. The run's summary holds the links, `https://pb2dfczv1ag1oogd.public.blob.vercel-storage.com/win/Jaspers-Terminal-Setup-<version>.exe` and `https://pb2dfczv1ag1oogd.public.blob.vercel-storage.com/mac/Jaspers-Terminal-<version>-arm64.dmg`.
4. A failed run is re-run in place with `gh run rerun <run id> --failed` once the cause is fixed, which runs the failed job again and leaves the platform that shipped alone. Never delete and re-push the tag: secrets are read fresh on every run, and a build never ships until its last step, so nothing partial is out there.

Between the signer check and the upload, `npm run test:packaged` installs the installer silently into a folder of its own and drives the installed app with Playwright (`tests/packaged.test.ts`, on `playwright-core`, which brings no browsers): the welcome screen opens, the window was never on screen before the page had rendered, Settings is in the menu bar, main says it is the packaged build of this version, `app-update.yml` names the feed and the signer the repo configured, setup is skipped and a note lands on the grid, and the tree says the build updates itself. The Mac job runs the same test against the `.app` it built, once `codesign` has verified its Developer ID signature and `stapler` its notarization ticket: `APP_BINARY="dist/mac-arm64/Jaspers Terminal.app/Contents/MacOS/Jaspers Terminal" npm run test:packaged`, which works on any Mac build. A failure blocks the upload; the screenshot it takes is the run's `smoke-test-windows` or `smoke-test-mac` artifact either way. Actions > Release > Run workflow is a dry run of both jobs on any branch: built, signed, notarized, and smoke tested, nothing uploaded.

Installed apps see the release within four hours, or at their next launch, and install it when they quit; the tray's Restart to update installs it at once. The feed is one file per platform folder, `latest.yml` or `latest-mac.yml`, so a release replaces the previous one for every install: there is no channel or staged rollout.

To sign and notarize on your own Mac, the certificate goes in the login keychain and `APPLE_API_KEY` is the path of the `.p8` file, next to the other two variables; without them `npm run dist` skips what it lacks.

The Windows secrets were set on 2026-09-22 and the Mac's on 2026-09-29, all read only by `release.yml`:

- `AZURE_TENANT_ID` and `AZURE_CLIENT_ID`: the directory and application ids of the `jaspers-terminal-release` app registration in Entra. Identifiers, not secrets, kept as secrets for convenience.
- `AZURE_CLIENT_SECRET`: a client secret of that app registration, its **Value** column, never its Secret ID. The wrong one fails signing with `AADSTS7000215: Invalid client secret provided`. A secret expires (24 months at most): make a new one under Certificates & secrets and replace the repo secret before it does, or releases fail at signing.
- The app registration holds the Artifact Signing Certificate Profile Signer role on the `signing-jaspers` account (resource group `rg-jaspers`, East US). The portal's member picker cannot find a service principal from a Guest account; Cloud Shell can: `az role assignment create --assignee-object-id <enterprise app object id> --assignee-principal-type ServicePrincipal --role "Artifact Signing Certificate Profile Signer" --scope <account resource id>`.
- `CSC_LINK`: the Developer ID Application certificate with its private key, a `.p12` in base64, and `CSC_KEY_PASSWORD`, its password. electron-builder imports it into a keychain of its own. The certificate, `Developer ID Application: Jaspers, Inc. (35T5S645NF)`, expires on 2031-09-17. A new one comes from developer.apple.com > Certificates, as the Account Holder; since Squirrel.Mac checks the team and not the certificate, updates keep working across it once `mac.identity` names it.
- `APPLE_API_KEY`: the contents of the `.p8` file of `Jaspers Terminal notarization`, a team key in App Store Connect > Users and Access > Integrations with the Developer role; `APPLE_API_KEY_ID` is its Key ID and `APPLE_API_ISSUER` the Issuer ID above the list of keys. The job writes the key to a file, since electron-builder reads a path. It does not expire; if it leaks, revoke it there and make another.
- `RELEASES_BLOB_TOKEN`: the read-write token of the `terminal-releases` store in the `jaspers` Vercel team, from the store's page in the dashboard.

The signing values in `electron-builder.yml` are the account `signing-jaspers`, the certificate profile `jaspers-terminal`, the East US endpoint, and the publisher `Jaspers Inc.`, which is the certificate's subject CN; the workflow fails the release if the built installer's signer differs. electron-builder 26 signs through the `TrustedSigning` PowerShell module, the service's older name; the service is now called Azure Artifact Signing, and its roles are named after it. On the Mac, `mac.identity` is the certificate's name, `Jaspers, Inc. (35T5S645NF)`: electron-builder signs with no other, and the job fails the release if the app is not signed with a Developer ID or carries no notarization ticket.

`src/main/app/updates.ts` runs electron-updater in packaged builds on Windows and macOS: a check after launch and every four hours, a download in the background, an install on quit, and never a restart on its own. What the tree shows through it is decided in `src/shared/app/updates.ts`. The builder writes `publish` into the package as `app-update.yml`, on Windows with the signer's name from `azureSignOptions.publisherName`, and the installed app refuses an update signed by anyone else; the workflow checks the installer against that name before uploading, since a wrong name would refuse every update after it. On a Mac, Squirrel.Mac installs an update only if it is the same app signed by the same team as the running one. So `mac.identity` pins the certificate, a preview or an unsigned build refuses every update, and a Mac app from before the Developer ID is replaced by hand once.
