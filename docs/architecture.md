# How it works

Jaspers Terminal is an Electron desktop application for public-market research built around an open-inference agent harness that runs with local, open-weight, or cloud language models (including Ollama, vLLM, `llama.cpp`, LM Studio, OpenRouter, Groq, Jaspers One, and direct cloud providers). The main process owns the single state tree, runs the Central orchestrator and numbered Grid Room agents, connects to MCP servers, records fetched data into a local SQLite store, and builds plugins through its built-in coding agent. Windows render what main pushes to them and send actions back; sandboxed plugins fill the grid.

## Open-inference harness: prompt bounds, context offloading, and loop recovery

Rather than appending raw tool responses, multi-thousand-row datasets, and full filing text directly to the conversation history, the harness bounds prompt size and recovers from local and small-model failure modes through four mechanisms:

1. **Bounded Zod `state` and `output` contracts (`STATE_MAX` & `OUTPUT_MAX`):**
   Every grid view declares Zod schemas for `state` (what the assistant writes via `place_view` or `set`) and `output` (what the view reports back via `usePublish(panel, output)`). In every round's prompt (`src/shared/agent/prompt.ts`), each panel's serialized `state` is bounded to 2 KB (`STATE_MAX = 2048`) and its `output` is bounded to **4 KB** (`OUTPUT_MAX = 4096`, also enforced by `setPanelOutput` in `src/main/actions.ts`). State mutations are coerced and validated against the view's Zod schema (`coerceViewState` and `setPanelStateChecked`), returning schema validation errors instead of writing invalid UI state.
   When a view renders long documents or tables (such as an SEC filing, earnings transcript, or full series), it publishes up to 200,000 characters (`PANEL_TEXT_MAX = 200_000`) via `usePublishText(panel, text)` to `panels/<id>/text`. That text is not injected into the round prompt; the assistant reads it on demand in paginated slices via `get { path: "panels/<id>/text", offset }` (`src/main/agent/tools/state.ts`).

2. **SQLite context offloading (`~/Jaspers/data/jaspers.db`):**
   Every source invocation is recorded by a dedicated store process (`src/store/db.ts`) into `~/Jaspers/data/jaspers.db` (opened in WAL mode with `0600` file permissions):
   - `runs` — one row per source execution (`id`, `source`, `args`, `args_hash`, `workspace`, `fetched_at`, `row_count`, `meta`, `text`, `error`).
   - `run_rows` — each returned object stored as an indexed JSON row (`run_id`, `idx`, `data`), queryable with `json_extract(data, '$.field')` so the model can filter, join, and aggregate across providers and sessions.
   - `docs` — an external-content FTS5 full-text index (`create virtual table docs using fts5(text, content='runs', content_rowid='id')`) over `runs.text`, supporting phrase and BM25 search over filings and transcripts without storing duplicate text.
   - `watched` — rolling SHA-256 observations (`task`, `at`, `hash`, `text`, retaining the latest 20 per task) used by scheduled SQLite delta watches (see [Skills](skills.md)).
   - `threads`, `exchanges`, `usage`, and `notifications` — persistent conversation threads (`<workspace>`, `<workspace>/<loop>`, `build/<id>`), user-visible transcripts, daily token accounting by origin, and the notification inbox.

   The assistant queries `~/Jaspers/data/jaspers.db` through the read-only `query` tool (`src/shared/data/store.ts`), which enforces both a read-only SQLite connection (`new DatabaseSync(file, { readOnly: true })`) and `checkQuery` validation (single `SELECT` or `WITH … SELECT` statement only, default `QUERY_LIMIT_DEFAULT = 500` rows, max `QUERY_LIMIT_MAX = 2000` rows).

3. **Context set-aside (`read_again`), reading streaks (`keptWhole`), and portable threads (`portable`):**
   Every conversation thread is kept whole on disk, while `src/shared/agent/aside.ts` bounds the active wire prompt: once tool outputs in a request exceed `WHOLE_MAX` (`400,000` characters) or belong to earlier requests, long outputs (`LARGE = 1500` characters) are replaced in the prompt with a short header and a note naming `read_again "<callId>"`. The model can retrieve one or more full outputs on demand via `read_again` (passing a single ID, comma-separated IDs, or `calls`) rather than resending prior tool payloads on every turn. While the model is in a streak of `read_again` calls or paginated `get { path: "panels/<id>/text", offset }` reads (`keptWhole`), the preceding rounds in that reading streak stay whole in the prompt so multi-page filings can be synthesized together. If a model echoes a shortened `[… set aside: read_again "<id>" …]` string or list from an earlier turn back into a new tool call, `restoreInput` automatically restores the original full value from the thread. When you switch between cloud and local models in **Settings > Language model**, `portable` (`src/shared/agent/history.ts`) strips provider-specific replay payloads (such as thinking blocks) while preserving every user message, assistant reply, and tool call. A chat runs on one model: Central's on the provider's fast model at low effort, when it has one, a room's on the model Central chose for it or else the thinking model, and a plugin's build on the thinking model (`chatRunsOn` in `src/shared/agent/model.ts`). Everything that reads a chat's thread asks `modelFor(chat)` in `src/main/agent/utils/settings.ts`, so a thread is never converted back and forth between two models.

4. **Local-model loop recovery: context mending, cutoff restatement, and tool-call trimming (`agent.ts`, `stop.ts`, `rounds.ts`):**
   - **Automatic context-window mending (`mend` & `shorten`):** When a local or open-weight model hits its context window limit (either via a provider context-length refusal or `model_context_window_exceeded` stop reason), the loop automatically sets aside earlier tool results or withholds the largest unread tool outputs (`makeRoom`, down to `ROOM = 2/3`) and retries the round (`MENDS_MAX = 8`) without dropping turns from the SQLite store.
   - **Mid-call output-limit and turn-timeout restatement (`cutShort` & `resolveRoundFailure`):** When a model with a smaller output cap or slower local generation cuts off mid-tool-call (`length`, `max_tokens`, or `max_output_tokens`) or times out while buffering a large tool payload (`isTurnTimeout`), the truncated call is dropped without running and the round is restated (`CUTS_MAX = 2`) at low reasoning effort (`RESTATED_TIMEOUT_MS = 90_000`) with instructions to make smaller incremental calls (such as passing `old` and `new` to `set` or `edit_file` on one passage at a time).
   - **Duplicate and runaway `place_view` tool-call trimming (`trimToolCalls`):** Before executing a multi-call round, `trimToolCalls` (`src/shared/agent/rounds.ts`) simulates grid placements (`place_view`, `remove_element`, `move_element`, `resize_element`) and drops duplicate tool calls as well as runaway `place_view` calls that target unplaceable views or overflow `GRID_FULL` (recovering `stopReason: 'length'` to `'tool_calls'` when only a trailing excess call was cut off).

## Concurrent Grid Room agents (`room_1`, `room_2`, …)

Jaspers Terminal separates global Central orchestration across tabs from isolated per-room execution (`src/main/agent/orchestrator.ts`, `src/main/agent/router.ts`, `src/main/agent/loop.ts`, and `src/shared/loops/loops.ts`):

```mermaid
flowchart TB
  User["User Input (Central Composer or @room_N)"] --> Router["Central Orchestrator (orchestrator.ts)"]
  Router -->|"create_room (delegates model, systemPrompt, plugins & skills)"| Room1["room_1 (f1)<br/>Isolated agent, tile frame & thread"]
  Router -->|"update_room (handOver / sendToLoop)"| Room2["room_2 (f2)<br/>Isolated agent, tile frame & thread"]
  Router <-->|"read_room & search_rooms"| Room1
  Room1 -->|"use_plugin (on-demand schema load)"| Registry["Plugin & Skill Registry"]
  Room1 -->|"build_plugin"| Builder["Coding Agent (build.ts)"]
```

- **Central orchestrator (`src/main/agent/orchestrator.ts` & `src/main/agent/router.ts`):** Central maintains a single persistent conversation flow (`central`) across all tabs, compressed at sitting boundaries (`>= 4h` inactivity gap or `> 15m` cold launch) into a `<prior_session_summary>` plus recent exchanges, and clearable via `/clear` or the Clear button. Central has full context of every room across all tabs (`read_room`, `search_rooms`, `get`, `query`), answers simple queries (< 3–6 seconds, such as portfolio value, a quick quote, or a single shell command) directly in chat, and proposes setting up a Room (`create_room`) with user confirmation for extensive, multi-step, repeatable, or lasting work (including grid views, deep research, web/audio/file scraping, file downloads, or multi-step `~/Jaspers/shell` workflows so a room worker executes them without cluttering Central), exercising high delegation authority over the room's `model`, `systemPrompt`, `plugins`, and `skills`.
- **Isolated Room agents (`room_1`, `room_2`, …):** Every room has an agent running inside its sandboxed frame that is completely blind to the work of other agents. It loads full schemas only for the plugins assigned to its room, activating additional plugins on demand via `use_plugin`. Every room is saved in memory in chronological order of its last activity (including when its tab is closed) and can be retrieved or searched by keyword from the global Rooms directory (`LoopsDialog`) or by Central (`search_rooms`). Permanent deletion (`delete_room`) requires explicit confirmation.

## The Coding Agent (`build_plugin`) lifecycle

When a loop needs a data source, custom view, document generator, or MCP connection that isn't installed, it searches [Jaspers Hub](https://hub.jsprai.com) (`find_plugin`) first. When nothing on Hub fits, it calls `build_plugin` (`src/main/agent/build.ts`), launching the builder agent loop (`runBuild`):

1. **Prompt assembly (`reference.ts` & `prompt.ts`):**
   `runBuild` starts a quiet agent loop (`BUILD_ROUNDS = 40`, `maxTokens: 16_000`) on a dedicated persistent chat thread (`build/<id>`). Its system prompt (`builderSystem` in `src/shared/agent/build/prompt.ts`) embeds `REFERENCE` (`src/main/agent/build/reference.ts`), which imports [`docs/sdk-reference.md`](sdk-reference.md), [`docs/writing-a-plugin.md`](writing-a-plugin.md), `packages/sdk/src/context.ts`, `packages/sdk/src/llm.ts`, and the four starter templates in [`docs/templates/`](templates/README.md) (`feed`, `feed-table`, `document`, `connection`) via Vite `?raw`.
2. **Staging in `~/Jaspers/.build/<id>` (`folder.ts`):**
   For a new plugin ID, `openFolder` (`src/main/agent/build/folder.ts`) opens a staging directory at `~/Jaspers/.build/<id>`, outside the watched `~/Jaspers/plugins/` folder so unapproved code is never built or executed. The builder inspects any previously built plugin for the same service (`list_files`, `read_file`) or fetches API docs (`search_web`, `fetch_page` with `.md` and `/llms.txt` fallbacks), then writes the plugin's shell (`package.json`, `plugin.tsx`, and any view/helper files) with `write_file`.
3. **Security envelope approval (`install_plugin` & `.jaspers-build.json`):**
   The builder calls `install_plugin` (`src/main/agent/build/install.ts`) with a one-line `purpose` and every resource the plugin will reach: `hosts`, `capabilities` (`files`, `llm`, `tools`, `state`, `skills`, `web`), `secrets`, `connections` (`https://` MCP URLs only), `packages`, and `frames`. The user is shown this **envelope** alongside the complete staged files (`trustQuestion`). On **Build it**, the app writes `.jaspers-build.json`, installs any declared npm packages (`installPackages` with install scripts disabled and native binaries rejected), and moves (`landFolder`) `~/Jaspers/.build/<id>` into `~/Jaspers/plugins/<id>`.
4. **Dual esbuild compilation & envelope enforcement:**
   The plugin loader bundles `~/Jaspers/plugins/<id>` twice with esbuild (once for the view iframe and once to evaluate definitions in a restricted Node `vm` sandbox with a 2-second timeout) and verifies that declared hosts, capabilities, secrets, connections, packages, and frames stay within `.jaspers-build.json`. Any later edit that widens the envelope refuses to build until the user approves the delta (`widenQuestion`).
5. **Iterative compilation and verification (`edit_file`, `check_plugin`, & `run_source`):**
   The builder fills in each source and helper one piece per round with `edit_file`, calls `check_plugin` (`waitForBuild` in `src/main/agent/build/check.ts`) to await the watcher's rebuild and read any TypeScript, bundler, or schema errors, updates the files if diagnostics are reported, and executes `run_source` with a test argument before returning the finished plugin summary to the calling loop. If a build stops early for any reason, its files and `build/<id>` conversation stay intact so calling `build_plugin` with the same `id` resumes where it left off. See [Asking the assistant for a plugin](asking-for-a-plugin.md).

## The app

- **One state tree, owned by main.** The Electron main process holds the app's state and is the only thing that writes it. After each change it pushes the whole tree to every window. The interface never edits state; it sends actions to main.
- **The assistant runs in main.** Each request calls the model with what is installed in its prompt, and the grid, the work on it, the focused element's state, the time, and the scheduled tasks alongside each turn. It runs the tools the model asks for and repeats until the model answers, stamping responses and work product with a local-time completion timestamp (`as of YYYY-MM-DD <12h><am|pm> <TZ>`). The assistant in the box above the composer (and in the docked Central tile) oversees the workspace, routes work, and runs the app: it calls no plugin sources itself, but inspects rooms, panels, tasks, and the SQLite store (`read_room`, `search_rooms`, `get`, `query`) to reason over what is going on across the workspace and answer questions in words. It also answers about the app (the layout, the work on the grid, tasks, settings, plugins, keys, skills), arranges the grid, changes a setting when you ask (theme, open at login, grid size, the task budget, skills on or off, reconnecting or removing a plugin, the model and the voice and search providers; it asks before removing a plugin or switching a provider, and never touches Pro mode or Eye), and for anything that needs new plugin data, extensive multi-step scraping or shell work, or is to be placed or changed in a tile, it starts a room (`create_room`) or hands the request to the room it is about (`update_room`). When it only starts or hands over work, its part ends there: the box above the composer closes, and the work answers in its own tile. It knows the installed plugins by name only; a new room is set up by a call of its own (`setup.ts`, on the fast model at low effort) that reads everything installed and chooses the plugins and skills the room needs. Before the room starts you are asked, shown what the room is, its model and plugins, and its refined instructions, and nothing is made until you press Start; when it cannot tell what a request means, or whether it is for Central, for a room that exists, or for a new room, it asks. A request starts as it is sent: you can send another while one is still working, and each runs beside the others with its own trail and its own Stop, which ends it, keeping what it had done so far. Requests in flight do not see each other's work until one has ended; each sees the grid as it is. A question from one of them waits its turn behind a question already on screen, and says which request it came from. A scheduled task's run never holds up yours. The chat keeps every exchange of a conversation, across restarts, and scrolling up reads back through it. Central is sent the last three exchanges and the new request (with a `<prior_session_summary>` across sitting boundaries), with what those exchanges' tools answered at length as notes it can read again; switching the model goes on with the same conversation, and `/clear` or `/new` starts it over.
- **Every piece of work has a tile and an assistant of its own.** Each element on a window's grid but the docked chat is the tile of a room, named in its bar, with a conversation of its own that is kept across restarts. The views the room shows are laid out inside the tile, under its command line, on cells of the tile's own, drawn fitted to what is there: one view fills the tile, and a dashboard of ten is still one tile, which moves, resizes, minimizes, and maximizes as one. A view inside is resized by hand by an edge it turns to another view, on the tile's own cells: it stops against its neighbor, as a tile of a window does, so one is made smaller before the one beside it is made larger. The sides it shares with the tile resize the tile. A line typed in the command line at the top of the tile goes to that room's own run of the assistant: it is told of its own tile first and of the plugins its room uses, learning of another when it needs one (`use_plugin`), changes only its own views, places a new view inside its tile, and asks its questions and answers in the box, under the line. The box is folded to the line by default: a small label in the tile's bar says how the room stands, working with what it is doing now, done, failed, or asking, and pressing it opens the box under the line (which can be resized from 0% to 100% of the tile height). In a tile with no view yet, a run opens the box itself, so what the room is doing is what the tile shows, and the first view to load folds it. Open, the box shows the room's conversation: what was asked, the steps each run took, and the reply. What it found is said there, briefly unless it is a deep research room: it has no note to put its own words on the grid in, and the views under the line are for what the plugins show. It is sent its whole conversation, not the last three exchanges: every word of it, with what earlier requests found as notes that say how to read it again, so a small request in a tile does not carry everything the room ever fetched. Nothing is dropped from the conversation that is kept. One run at a time: a message sent while the room is at it joins that run, read with what it was just doing, and one sent as the reply is being written starts the next. The label in a tile's bar is that mark too, while its room is working or asking. Its minimize button leaves the tile as its bar, where it stands, with the cells under it free for others; what it showed is kept, a question waits, and the same button or a double click on the bar brings it back where it was, or to the nearest free cells. The bar ends in a menu, which a minimized tile keeps: what may be done (stop what the room is doing, rename the room, inspect or edit its instructions, close the room, or delete it, which ends it and forgets its conversation), then what the room's assistant was told of, with each connection and what it is doing, and the room's timeline. Work Central starts gets a tile at once, half a window unless the request says where, which shows what its own assistant is doing until that one's first view loads into it and folds the box. The box above the composer is one conversation for Central; it places no view itself, and a view placed by hand becomes a room of its own, in a tile it fills. A message typed there that starts with a room's name, `@room_3`, goes straight to that room, as if typed in its tile.
- **A piece of work is a room, and rooms are numbered.** Each is named by the number its workspace gave it when it was made, `room_1`, `room_2`, and so on, never by what it does; a number is never given twice, so a room keeps it through closing and reopening. Its bar shows its number and title, and that is how you name it to the assistant ("send this to room_3", "@room_3 use 30 days"). The cross on its bar closes it: its tile goes with every view in it and what it is doing stops, but the room is kept in memory, views and conversation. **Rooms** (in the top bar or **Settings > View loops**) opens the directory of every room across the terminal, open and closed, in chronological order of last activity, searchable by keyword, with when it was created, closed, and reopened. Reopen puts a closed room back where it was, or on the nearest free cells, and its assistant carries on with the conversation; Delete (after confirmation) forgets it for good. The assistant can close, search, and reopen rooms too when you ask.
- **Tasks run in main too.** One timer runs each task at its time: one tool call made directly, like refreshing a view, or a request to the assistant, whose reply joins the workspace's conversation. Work such a request starts stays within the task's limits: it is told it runs for a task, it asks for no key, a question it has to ask waits ten minutes and no longer, and it counts against the daily budget. The task's run lasts until that work is done, and what the task says is what the work said.
- **Connections** are MCP servers, over stdio or streamable HTTP. A plugin declares them in its `plugin.tsx`, or you add one in Settings and the app writes that plugin for you. Main keeps one client per connection. Keys, OAuth tokens, and the Jaspers sign-in's tokens never leave main; a server that signs its users in through Jaspers connects on that sign-in.
- **A server's own views.** An MCP server can ship a page for a tool's answer (MCP Apps). Main reads the page from the server and serves it on a scheme of its own, one origin per connection, with the policy the page declared. The built-in `core/app` view hosts it in a sandboxed iframe and passes what the page asks for to main, which checks each request against the panel it came from.
- **The store** is one SQLite file, `~/Jaspers/data/jaspers.db`. Every source run is recorded there with its arguments, its workspace, and the time, and the assistant reads it back with a read-only `query` tool. Each chat is kept there too, an exchange with what its run did and, when it failed, why. It runs in a process of its own, since SQLite is synchronous and main is what pushes state to the windows.
- **Plugins** are folders in `~/Jaspers/plugins/`, put there by hand or installed from Settings. Main builds each one, registers its views and sources, and renders its views in sandboxed iframes. A plugin with code of its own runs it in a separate process, reaching the app only through capabilities it declares. A plugin's view that is waiting on you, for a key the plugin declares or a sign-in to one of its connections, asks for it in its own element.
- **Skills** are folders with a `SKILL.md`, in `~/Jaspers/skills/` or a plugin's `skills/` folder, in the [Agent Skills](https://agentskills.io) format. The assistant's prompt lists each skill's name and description. When a request fits one, or the user types `/name`, the assistant loads that skill's instructions with a tool, and reads the skill's other files with another. A plugin's own model loads them the same way through its `skills` capability. See [Skills](skills.md).

## How a plugin connects to the app

A plugin adds views and data sources.

- A **view** is a React component that lives in a grid element. The assistant places it, changes what it shows by writing its state, and reads back what it shows.
- A **source** is a named data call, usually one tool on an MCP server. Views and the assistant both run sources.

```mermaid
flowchart LR
  folder["~/Jaspers/plugins/watchlist/plugin.tsx"] --> loader["Loader in main<br/>esbuild, sandboxed eval, validation"]
  loader --> registry["Registry<br/>views and sources"]
  registry --> tree["App state"]
  tree --> agent["Assistant<br/>prompt and tools"]
  tree --> frame["View in a sandboxed iframe"]
  frame <-->|"bridge: state, output, sources"| main["Main<br/>checks writes, runs sources"]
  agent -->|"place_view, set, get, source tools"| main
  main --> mcp["MCP connections"]
```

1. **Discovery.** The app looks for folders with a `plugin.tsx` in `~/Jaspers/plugins/` (or `$JASPERS_HOME/plugins/`), whether you put it there or installed it. The folder name is the plugin id.
2. **Build.** Main bundles the folder with esbuild twice: once for the view's iframe, and once to read the definitions. Everything the plugin imports is bundled in, found in the plugin's own `node_modules`, except what the app provides: `react`, `react-dom`, `zod`, and `@jaspers-ai/sdk`.
3. **Definitions.** The definitions run once in a sandbox with no file system, no network, no Node globals, and a 2 second limit. React is a stub there, so components never run in main.
4. **Registration.** Main checks the definition, then registers its connections, sources, and views as `<plugin>/<name>`, like `watchlist/quotes`.
5. **What the assistant sees.** A piece of work's assistant is told each of its plugins' views with the state keys it takes, and each source with its connection's status; the one in the global box is told what each view is, and the sources. Either calls sources through `run_source { source, input }` and asks `describe_source` for a full input schema when needed. For the watchlist below:

   ```text
   - watchlist/watchlist: Watchlist. Renders watchlist/quotes. state: { tickers }
   - watchlist/quotes: Quotes for ticker symbols: name, price, and the day's change as a fraction. — takes tickers [connection watchlist/server: ready]
   ```

   A piece of work's assistant is told where its tile is, how the views inside it are laid out, and for each of them the view's `instructions`, state, and output. The one in the global box is told each tile with the views inside it, and which tile is focused.

6. **Placing and driving.** A piece of work's assistant calls `place_view { view: "watchlist/watchlist", state: { tickers: ["AAPL"] } }`, which puts the view inside its tile, changes the element with `set panels/e1/state/tickers ["MSFT"]`, and reads it with `get panels/e1/output`. Main checks every state write against the view's schema and rejects invalid ones with the reason.
7. **Rendering.** Each plugin view gets its own sandboxed iframe with no network and no reach into the app. A plugin can declare sites its views may show in a frame, as the TradingView chart does. The app supplies React, zod, and the SDK. The view talks to the app only through the SDK hooks, which pass messages to main.
8. **Sources run through main.** Main calls an MCP connection or delegates a function source to its plugin host, keeps the rows, and hands them to the view. Two runs with the same arguments within 60 seconds share one call. Keys never reach a plugin.
9. **Hot reload.** Saving any file in a plugin folder in `~/Jaspers/plugins` rebuilds the plugin and remounts its views, and each element keeps its state and output. A failed build keeps the last good version running and reports the error.

## Project layout

```
src/main/agent/    The assistant's loop and its helpers under utils/, orchestrator.ts, loop.ts, router.ts, setup.ts, its threads and memory, the tool families under tools/, the plugin builder (build.ts and build/), and the web under web/
src/main/loops/    Loop records in the state tree
src/main/tasks/    Scheduled tasks and SQLite delta watch execution (tasks.ts), paired with clock-rule.ts, market-calendar.ts, and delta.ts in src/shared/tasks/
src/main/skills/   Agent Skills discovery, editing, installation, and assistant-authored skills
src/main/llm/      Provider request protocols and stream readers
src/main/plugins/  Plugins, their hosts and capabilities, installs, connections, and MCP Apps
src/main/hub/      Jaspers Hub: the directory's listings, and publishing a plugin or skill of the user's own
src/main/eye/      Opt-in live feedback sharing and one-shot feedback
src/main/          Main process: the state tree and its actions at the root, a folder per area beside them
src/preload/       The bridge between the interface and main
src/renderer/      Interface: React, TypeScript, Tailwind CSS v4
src/plugin-host/   Isolated utility process running plugin backend sources and jobs
src/host-runtime/  What a plugin view's iframe loads (jaspers-host://runtime/): React, zod, the SDK
src/store/         The store process (db.ts): the SQLite file (~/Jaspers/data/jaspers.db) every source run is kept in
src/shared/        Types and pure logic shared across processes, a folder per area
packages/sdk/      @jaspers-ai/sdk: what views and plugins are written against
scripts/           Build scripts: the plugin view runtime, the SDK package
electron-builder.yml  Packaging for `npm run dist`
```

Built with Electron and electron-vite. Contributor commands and rules live in [CLAUDE.md](../CLAUDE.md); implementation constraints are in [Development](development.md).
